What Could Go Wrong?

Plain-language explanation of risks for each High and Medium finding, written for non-technical readers.

High Qurban participant data may be inaccessible

The database table that stores the names and details of Qurban participants has a security rule enabled that blocks all access — but the app forgot to specify who is actually allowed in. This means the data for Qurban participants could be silently empty for all users, or worse, completely unprotected. If left unresolved, staff cannot see participant lists and reports will be missing data.

High Dashboard will slow down significantly as data grows

Every time someone opens the dashboard, the app downloads the entire transaction history (every zakat payment ever recorded) just to count totals. This works fine today with a few hundred records, but as years of data accumulate, the dashboard will become progressively slower — potentially taking tens of seconds to load — and could crash for users with slow connections.

Medium Search boxes send too many database requests

Three search boxes in the app (Warga data, Mustahik data, and Qurban participant search) fire a database request on every single character the user types, instead of waiting for them to pause. This means searching "Ahmad" triggers 5 separate database calls. Under normal usage this is wasteful; under heavy concurrent use, it could overload the server.

Medium Financial records cannot be recovered once deleted

When a zakat payment or distribution record is deleted, it is permanently removed from the database with no recovery option and no record of who deleted it or when. For a financial system managing charitable funds, this is a compliance risk — there is no audit trail for deletions.

Medium External websites can probe the invitation system

The system that manages user invitations (sending and validating invitation links) is currently configured to accept requests from any website on the internet. While the invitation validation itself is secure, the open access policy is broader than necessary and could enable automated probing of the invitation token system.

Medium CSV import bypasses data type checking

When staff upload a CSV file to bulk-import citizen (Warga) records, the app skips the normal type-checking step that ensures the data matches the expected format. This means malformed or unexpected values could be inserted directly into the database without validation.

Medium Hak Amil calculation uses two different methods simultaneously

The system calculates the mosque's Hak Amil share (administrator fee) using two separate, independent methods that may produce different totals. This could lead to discrepancies in financial reports depending on which view a user is looking at, creating confusion for auditors or board members reviewing the financial statements.

Medium Distribution stock check reads from the wrong source

When checking how much rice or money is available to distribute to recipients, the system reads from an older, legacy table rather than the current transaction records. This means the available stock figure shown to staff may not accurately reflect the true balance, potentially allowing over-distribution.

Credential & API Key Exposure

Low Credentials SEC-09 — Mock credentials bundled into production build (offline mode) src/lib/mockAuth.ts · src/pages/Login.tsx:104-106

Description: When VITE_OFFLINE_MODE=true, the Login page renders mock credentials (email + plaintext password) directly in the UI. Scalability Assessment

⚡ Verdict: Partial — App handles current load but will fail at 5–10× growth

The primary bottleneck is usePembayaranList in useMuzakki.ts, which implements a textbook N+1 query pattern. For each row in a 20-item page, it fires 2 additional queries — one against pemasukan_uang and one against pemasukan_beras — both filtering by muzakki_id without an index. A single page load currently fires 41 Supabase queries. At 10× user load, the Free tier's 500,000 API requests/month would be exhausted in days rather than months, and the lack of an index on pemasukan_uang(muzakki_id) means each of those 40 sub-queries performs a sequential scan of the entire table.

The second structural problem is useDashboardStats in useDashboard.ts, which fires 10 sequential full-table-scan queries with no limits and runs a 30-second auto-refresh interval (refetchInterval: 30000). With staleTime: 0 (the React Query default used by all 28 hooks in the codebase), every user who opens the dashboard — or switches browser tabs — triggers a fresh batch of 10 queries. At 10× users with a 30-second polling interval, the database receives approximately 10 queries × N users every 30 seconds. Combined with the 60-connection limit on the Free tier and no PgBouncer connection pooler (Pro-only), connection exhaustion will occur before significant user volume is reached.

1. High N+1 query in usePembayaranList — 41 queries per page load
